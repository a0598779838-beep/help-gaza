# دليل غزة للمساعدات — Gaza Aid Guide

منصة عربية باتجاه RTL لفهرسة إعلانات المساعدات المنشورة وربطها بمصادرها الرسمية. المشروع دليل معلوماتي مستقل، ولا يقدم مساعدات ولا يضمن قبول التسجيل. لا تجمع الواجهة طلبات المستفيدين أو وثائقهم.

## الحالة الحالية

- يعمل الموقع محليًا دون إعدادات خارجية، ويعرض روابط المواقع والتسجيل التي أُضيفت إلى دليل الجهات. بعض الروابط لا يمكن التحقق من استمرار فتح التسجيل فيها؛ تحقق من الجهة والرابط قبل مشاركة بياناتك.
- بعد إعداد Supabase، يقرأ الموقع الإعلانات المنشورة والمعتمدة من قاعدة البيانات. البحث والتصفية والترقيم تتم باستعلام PostgreSQL (`search_public_aids`).
- دخول لوحة الإدارة لا يمنح صلاحية تلقائيًا؛ يجب أن يكون حساب Supabase موجودًا مسبقًا وأن يمنحه مسؤول قاعدة البيانات دور `admin`.
- إرسال البلاغات يحتاج نشر Edge Function وإعداد أسرارها. لن يتم تخزين بيانات المستفيدين.
- لم يتم إنشاء مشروع Supabase أو نشر الموقع من هذه البيئة.

## المتطلبات

- Node.js 20.19+ أو 22.12+ (متوافق مع Vite 7).
- npm.
- مشروع Supabase عند تفعيل التخزين والمصادقة والبلاغات.

## التشغيل المحلي

```powershell
npm install
npm run dev
```

افتح العنوان الذي يظهر في الطرفية. دون `.env` تُحمّل الجهات من البيانات المحلية، وتظهر بطاقة مساعدة توضيحية موسومة بوضوح؛ لا تمثل هذه البطاقة إعلانًا حقيقيًا.

أوامر الجودة:

```powershell
npm run typecheck
npm run lint
npm test
npm run build
npm run preview
```

## إعداد Supabase

1. أنشئ مشروع PostgreSQL في Supabase.
2. انسخ `.env.example` إلى `.env`، ثم ضع عنوان المشروع ومفتاح `anon` العام:

   ```dotenv
   VITE_SUPABASE_URL=https://PROJECT_REF.supabase.co
   VITE_SUPABASE_ANON_KEY=PUBLIC_ANON_KEY
   ```

   لا تضع مفتاح `service_role` في `.env` الخاص بالواجهة أو في مستودع Git. ملف `.env` مستثنى من Git.

3. طبّق ملفات الترحيل في `supabase/migrations/` بالترتيب عبر Supabase SQL Editor أو Supabase CLI. ينشئ الترحيل الأول المخطط والجداول والفهارس والقيود وRLS والتصنيفات، ويضيف مرجع WFP الأساسي. يضيف الترحيلان التاليان حقلي رابط خط المساعدة ورابط التسجيل المباشر. `supabase/seed.sql` اختياري لإدراج الجهات والتصنيفات الأولية دون تكرار؛ لا ينشئ أي إعلان مساعدة.
4. أنشئ حساب المشرف يدويًا من Supabase Authentication، ثم عيّن دوره من SQL Editor باستخدام UUID المستخدم الذي أنشأته:

   ```sql
   insert into public.profiles (id, display_name, role)
   values ('AUTH_USER_UUID', 'اسم المشرف', 'admin')
   on conflict (id) do update set role = 'admin';
   ```

   لا تنشئ مسار تسجيل مشرفين عامًا. تعيين الدور امتياز إداري ويجب تنفيذه من حساب موثوق في لوحة Supabase.
5. شغّل المشروع من جديد. تعرض الصفحات العامة المساعدات المنشورة والمعتمدة فقط؛ RLS وقيود RPC تفرضان ذلك في قاعدة البيانات أيضًا.

### تشغيل البلاغات

انشر `supabase/functions/submit-report` باستخدام Supabase CLI، واضبط الأسرار في مشروع Supabase (وليس في Vite):

```powershell
supabase secrets set SUPABASE_SERVICE_ROLE_KEY=YOUR_SERVICE_ROLE_KEY
supabase secrets set ALLOWED_ORIGIN=https://YOUR_SITE_DOMAIN
supabase secrets set RATE_LIMIT_SALT=LONG_RANDOM_SECRET
supabase functions deploy submit-report
```

تستخدم الوظيفة مفتاح الخدمة داخل بيئة الخادم فقط، وتتحقق من الحقول والروابط، وتحد البلاغات إلى 3 في الساعة لكل بصمة عنوان شبكي. لا تخزن جدول حدود المعدل عنوان IP نفسه. قبل الإنتاج، تحقق من أن منصة الوظائف تضع `x-forwarded-for` بطريقة موثوقة، واضبط `ALLOWED_ORIGIN` على نطاقك الفعلي. يجب الاحتفاظ بمفتاح الخدمة وسر الحد من المعدل خارج المستودع.

## النشر

### Vercel

1. ارفع المستودع إلى GitHub.
2. استورد المشروع في Vercel. إعداد Vite الافتراضي يستخدم `npm run build` ومجلد `dist`.
3. أضف `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY` إلى إعدادات البيئة في Vercel، ثم أعد النشر.
4. استبدل النطاق التجريبي `https://example.invalid` في `public/sitemap.xml` و`public/robots.txt` بعنوان الموقع النهائي قبل النشر، وأضف عناوين صفحات التفاصيل العامة المنشورة. لا تضع بيانات خاصة في sitemap.
5. أضف نطاق Vercel إلى إعدادات Supabase Auth redirect URLs وسياسة CORS المناسبة.

يمكن أيضًا نشر مجلد `dist` على أي استضافة ملفات ثابتة تدعم إعادة كتابة المسارات إلى `index.html` لتطبيقات SPA. ملف `vercel.json` يضبط إعادة الكتابة لـ Vercel.

## الأمان وإدارة المحتوى

- لا تسمح سياسة RLS للزائر بإنشاء أو تعديل أو حذف مساعدات.
- صفحات الإدارة تعتمد على Supabase Auth والتحقق من `profiles.role`، مع تكرار التحقق في سياسات PostgreSQL.
- الإعلانات الجديدة تنشأ كمسودات `pending_review`. لا تنشر إعلانًا إلا بعد مراجعة الإعلان الأصلي والرابط الرسمي يدويًا.
- لا يجلب النظام صفحات خارجية تلقائيًا ولا ينفذ scraping. روابط HTTPS/HTTP فقط؛ لا توجد معاينة خادمية للروابط.
- البلاغات غير عامة؛ قراءتها وتغيير حالتها مقصوران على المشرف. بريد التواصل اختياري.
- لا تفعّل الإعلانات أو التحليلات قبل إعداد الموافقة والامتثال القانوني اللازم.
- مساحة الإعلان في الرئيسية غير مفعلة ولا تحمل إعلانات أو تتداخل مع روابط التسجيل.

## الصفحات والميزات

- الرئيسية، البحث، التصنيفات، التصفية حسب النوع والمنطقة والحالة والجهة، والترقيم.
- صفحة تفاصيل لكل مساعدة مع الحالة والتواريخ والمصدر ونطاق الرابط وأزرار النسخ/المشاركة والإبلاغ.
- دليل الجهات، عن المنصة، التواصل والبلاغ، الخصوصية، وشروط الاستخدام.
- لوحة دخول المشرف، إنشاء مسودات، مراجعة/نشر بعد توثيق المصدر الرسمي (رابط التسجيل اختياري إذا لم يذكره المصدر)، متابعة البلاغات وسجل التدقيق والإحصاءات الحقيقية.
- تصميم responsive، RTL، حالات التحميل والخطأ والفراغ، وعناوين ووصف صفحات.

## ملاحظات SEO

التطبيق الحالي Vite SPA؛ يعرض عناوين ووصفًا خاصًا بالمسار بعد تشغيل JavaScript، وهذا ليس بديلًا كاملًا عن SSR أو prerendering لمحركات البحث التي لا تنفذ JavaScript. قبل الاعتماد على فهرسة تفاصيل الإعلانات أو مشاركة OG الديناميكية، أضف SSR/prerender مناسبًا أو انقل طبقة التقديم إلى إطار يدعم SSR. Sitemap المرفق ملف بداية ثابت ويجب تحديثه بالنطاق وروابط التفاصيل المنشورة.

## الاختبارات

الاختبارات الحالية تغطي التحقق من الروابط، حالة انتهاء الموعد، البحث والترشيح والترقيم في الوضع التجريبي. اختبارات RLS والمصادقة والبلاغات تتطلب مشروع Supabase مهيأ؛ اختبرها في بيئة staging قبل النشر.
